# 5. Deployment and monitoring

## Roll out in stages

1. **Me.** Use it on my own work until the daily failures stop being surprises.
2. **A few real users.** Pick two or three people who ask different kinds of questions. Watch their corrections; they are the cheapest test set you will ever get.
3. **The team.** Only after the evaluation set passes and the pilot's corrections have turned into rules and cases.

Confirm the audience before writing instructions. Scope drift is expensive: re-scoping a shared agent from "a narrow tool" to "broad enough that people never switch away" to "this specific team only" meant rewriting its instructions twice.

## What to log

One event per request, with the minimum that answers "is it getting better or worse, and what changed when it did":

```
ts, session, category, tools, tool_errors, corrected, turns, latency_ms, rules_version
```

`rules_version` is the one people forget. Without it a bad week cannot be tied to the change that caused it.

## The weekly report

```bash
python3 -m monitor report --logs monitoring/sample_logs.jsonl
```

```
week       events  corrected  tool errors  median turns   p95 ms  instructions
2026-W12       42        10%           2%             2     5248  v13
2026-W13       46        28%          22%             2     5328  v14
2026-W14       45         7%           2%             2     4603  v15

Alerts:
  2026-W13: correction rate 28% vs 16% before (instructions v14)
  2026-W13: tool error rate 22% vs 4% before (instructions v14)
```

The log is **synthetic**, generated by `monitoring/make_sample_logs.py` with a fixed seed. It shows what the report and an alert look like. It says nothing about any real agent.

## About the alert rule

A week alerts when its rate is above the mean of the previous three weeks by both an absolute margin (5 points) and a relative one (1.5x), and only when there are enough events. That avoids "1% to 2%" alerts.

It is still noisy at about 45 events a week: when I generated the sample log, several random seeds produced an alert in a week where nothing had changed. So an alert is a prompt to look at the `instructions` column and the failing cases, not a verdict. At low volume, prefer reading the corrected conversations to trusting any threshold.

## Incident template

Symptom, how it was detected, root cause, the rule changed, the case added to the evaluation set. The last two are what turn an incident into protection.
